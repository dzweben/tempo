open-source research software

tracking · engagement · messaging · participant outreach

Research studies that follow the same people for years have to keep contacting them: a reminder before a visit, a survey to fill in afterwards, check-ins in between. Who needs what, and when, depends on each person's own dates and on which forms they have already completed. Studies keep all of that in a database like REDCap or Qualtrics.

TEMPO reads that database and runs the contacting. Visit reminders, survey invitations and the follow-ups that chase them, prompts that have to arrive at an exact minute, compensation notices. It also tracks the other direction: which forms each participant has completed, where they are in their sequence, and what the study is still waiting on.

Texts go out through the study's own phone number, so a participant can just reply and the whole exchange sits in one thread a coordinator picks up. Anyone who texts STOP is silenced everywhere, automatically.

You set it up by writing rules against database fields. Fourteen days after the baseline visit, while that form is still incomplete. Completing one survey can be what makes the next message due, which is enough to run a protocol lasting years.

01
How it works

From a date field to a sent message

Each run does the same five things: export the current records, expand the rules into dated rows, pick the rows that are due now, send them, and log what went out.

01 pullExport the study out of REDCap or Qualtrics over the API, one call per event, and stitch it together on record_id so you end up with a single row per participant holding their dates, the completion flag on each instrument, and their contact details.›
02 expandRun every rule against that row. Fill in the [event][field] references with that person's values, fetch the survey URLs the message needs, do the date arithmetic, and you get one dated line per participant for each time the message is owed.›
03 selectNarrow that down to the lines falling in this run's window, and check each one's condition against the completion flags as they stand right now. Drop anyone who opted out, anything inside quiet hours, anything whose link did not resolve, and anything the ledger says already went.›
04 sendClaim the line so nothing else can take it, render the body with that person's details and survey URL in it, and POST it to the messaging provider or hand it to SMTP.›
05 recordWrite pid | alert | timestamp | channel | recipient to the ledger. That line is what every later run checks against, which is how the same message never goes out twice.›
the grid

A rule produces the date. Fourteen days after the baseline visit, repeating weekly, up to three times, while the form is still incomplete. Each run evaluates those rules against the current roster and produces one row per participant for each time a message is due, with the timestamp, the destination and the message body already filled in. Those rows are the whole schedule for the study.

The grid is thrown away and rebuilt on every run. The only thing kept between runs is the ledger of what has been sent. That is what makes fixing things cheap: if a coordinator corrects a wrong visit date in REDCap, every message anchored to that date is right on the next run.

Picking what to send is a filter on that grid: rows inside the current run's window whose condition still holds against the current completion flags, minus anyone who opted out, anything falling in quiet hours, anything whose survey link did not resolve, and anything already in the ledger.

what counts as a trigger

A rule has two parts and both point at the survey platform. The condition that decides whether a message is owed is a field reference, written [event][field], and so is the date it counts from. There is no list of message types in the code and no special case for momentary assessment or for visit reminders. A condition is a field that is not marked complete. An anchor is a date field on some event.

Because of that, schedules chain without anyone sequencing them. Completing an instrument changes a field that another rule is watching. Record a visit and its questionnaires come due. Complete those and their reminders stop, and the visit date becomes the anchor for the next phase. Nobody writes that ordering down. It comes out of the field references, which is why a three-year protocol that branches on what participants do is still a flat list of rules.

the clock

Nothing runs continuously. Cron invokes the pipeline, and the only requirement is that it runs often enough that no slot falls between runs. A reminder due at 5pm is covered by a run at 5pm. A prompt that has to arrive at 8:10 needs runs that overlap that slot, because cron will not fire at exactly 8:10:00. The run picks the slot up early and waits in process until the scheduled second.

You can run it as often as you want. Each run rebuilds the grid from a fresh export and checks the ledger before sending, so an extra run finds nothing to do and exits. How often you run it depends on how precise the timing needs to be.

what it plugs into

The build here uses REDCap, OpenPhone and Gmail SMTP. Swapping any of them means reimplementing a few calls; Qualtrics, Twilio and SES offer the same operations.

Integration pointWhat TEMPO needs from it
Survey platformA record export, date fields, per-form completion flags, and a per-participant survey link
SMS providerA send endpoint. Optionally a message-history endpoint, used to arbitrate against duplicates
EmailSMTP credentials, or any HTTP send API
SchedulerAnything that can invoke a URL on a schedule — cron, a platform cron trigger, or a CI timer

Sample code

Declaring and sending a message

Field names below are placeholders for your own event and instrument names. 

{
  instrument: "Follow-up reminder",

  // Owed only while the form is still incomplete.
  condition: "[followup_arm_1][followup_1_complete]<>2",

  // 14 days after the baseline date, then every 7 days, at most 3 times.
  sendDateSpec: "14 days after [baseline_arm_1][baseline_date] " +
                "repeat every 7 days up to 3 times",

  // A phone field implies SMS, an email field implies email.
  destinationSpec: "[baseline_arm_1][participant_phone]\t[baseline_arm_1][participant_email]",

  // [event][field] fills per participant; [survey-link:form] becomes
  // that participant's own URL, resolved at send time.
  message: "Hi [baseline_arm_1][first_name], your follow-up is open: " +
           "[followup_arm_1][survey-link:followup_1]",
}
Declaring a message. A single entry sets the condition under which the message is owed, the send time, the destination fields and the body.
const anchor = participant.fields["baseline_date"];   // "2026-03-04"
const { offsetDays, everyDays, maxTimes } = parseSpec(alert.sendDateSpec);

const sends = [];
for (let n = 0; n < maxTimes; n++) {
  if (isComplete(participant, alert.condition)) break;   // responded, stop
  sends.push(atStudyTime(addDays(anchor, offsetDays + n * everyDays), "17:00"));
}
// → 2026-03-18T17:00, 2026-03-25T17:00, 2026-04-01T17:00
Computing the send time. The send time resolves per participant against their own dates, and repeats stop once the completion flag flips, so responders are not chased.
await fetch("https://api.openphone.com/v1/messages", {
  method: "POST",
  headers: { "Content-Type": "application/json", Authorization: API_KEY },
  body: JSON.stringify({ content: body, from: FROM_NUMBER, to: [e164] }),
  signal: AbortSignal.timeout(30_000),
});
Sending a text. The send is one POST to the provider's messages endpoint, so any provider that exposes one fits here.
const mailer = nodemailer.createTransport({
  host: "smtp.gmail.com", port: 587, secure: false,
  pool: true, auth: { user: SMTP_USER, pass: SMTP_PASS },
});

await mailer.sendMail({ from, to: recipient, subject, text: body });
Sending an email. SMTP is pooled, so a batch of messages reuses one connection.
not sending it twice

Three separate checks have to fail before the same message goes out twice. Duplicates matter more here than in most software: a repeat text, or one that arrives at 3am, is a protocol deviation the study has to report, and many participants are minors.

MechanismWhat it catches
Append-only ledger
pid|alert|time|channel|recipient		The ordinary case: a rerun, a retry, an overlapping schedule
Claim before transmitTwo runs hitting the same slot; only one wins the claim
Provider history checkA send that happened but whose ledger write was lost

There are other guards around it. Nothing transmits outside the daily window. The opt-out list is checked when the queue is built and checked again right before sending, because somebody can opt out in between. A cap limits how much any one run can send, so a bad rule cannot blast the whole roster. A message whose survey link did not resolve is held back, so a broken link never reaches anyone. Dry-run is the default, and there is a switch that puts everything back into dry-run without waiting on a deploy.

03
Momentary assessment

Prompts on the minute

An EMA prompt asks what someone is doing right now, so it has to arrive when it was scheduled. A prompt that shows up forty minutes late is asking about a different part of that person's day, and the answer looks identical to a good one in the dataset.

sampling grid — 25 slots / 7 days
sent 0 queued 25 last —
scheduled sent quiet hours — no prompt scheduled now

The grid is a list of weekday and clock-time slots: Monday 8:10am, Monday 1:45pm, and so on. Every participant gets the same set of slots anchored to their own start date. Expanding it gives one row per prompt with that person's phone number and survey link attached. In the picture above, how far a stem reaches tells you the time of day, and the shaded columns are the hours when nobody gets texted. 

// A sampling grid: slots repeat across the period, anchored per participant.
const GRID = [
  { day: "Mon", at: "08:10" }, { day: "Mon", at: "13:45" }, { day: "Mon", at: "19:20" },
  // … 25 slots across the sampling period
];

for (const slot of GRID) {
  schedule.push({
    pid: participant.id,
    sendAt: atStudyTime(nextWeekday(startDay, slot.day), slot.at),
    phone: participant.fields["prompt_phone"],
    surveyLink: await resolveLink(participant, slot.form),
  });
}
Expanding the grid. The same weekday-and-clock-time slots for everyone, hung off whatever date that particular participant started on.
// Wait out the remainder in-process, then claim and fire.
const waitMs = slot.sendAt - Date.now();
if (waitMs > 0) await sleep(waitMs);

if (await claim(slot.key)) {            // lost the race? another run has it
  await sendSMS(slot.phone, render(slot));
  await ledger.append({ ...slot, status: "sent", latencySec: 2 });
}
Waiting out the remainder. Cron will not fire you at 8:10:00 exactly, so the sender does not try to make it. It wakes up on a coarse clock, grabs anything coming up soon, and then just sits there until the second arrives.

Runs can overlap, with one still waiting out a slot when the next is invoked, so a run claims a slot before it sends anything and only the run holding the claim transmits. If a prompt misses its window anyway, it is logged as skipped.

In practice they land two to four seconds after the second they were scheduled for. That number goes in the ledger next to every message, so if it ever starts drifting you can see it happening.
